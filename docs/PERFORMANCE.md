# Performance measurements and cache boundaries

GitHub source checks measure duplicate review with synthetic collections of **33,000 and 100,000 tracks**. They exercise the actual API filters, connected recording groups, evidence facets, a cold query and five subsequent 40-row pages. No private library is used. The `source-validation-ubuntu-24.04` artifact contains `performance.json` with elapsed time, incremental peak allocations and graph-build counts.

A generous CI budget catches accidental quadratic work: 60 seconds per cold query, 10 seconds per subsequent page and 600 MiB of incremental Python allocations. These are regression limits for the synthetic workload, not a promise about all hardware or complete library import time. Compare recorded measurements across equivalent runners before tightening them or changing the storage model. Browser rendering, audio hashing, native database extraction and archive compression need separate measurements.

Duplicate review retains **one filtered result per loaded catalog**. Paging or switching between pair and recording-group views reuses its sorted candidates and connected graphs. A changed filter, keeper policy, catalog description set, review decision, held conflict, file inventory or content verification replaces the result. Nested session changes are hashed by value, so modifying an existing dictionary cannot silently reuse stale evidence. Catalog source-derived changes must call the existing `refresh_counts()` method, which replaces the description set. Comments and other sidecar metadata do not rewrite captured duplicate evidence.

The cache retains no audio and writes nothing to source libraries. It intentionally spends linear time hashing current session evidence on every request; this is safer than relying on fragile invalidation flags scattered across mutation endpoints. If hashing becomes a measured cost, use a centralized revision model with equivalent invalidation tests before removing that check. SQLite indexes or full-text search should follow measurements of the actual query, rather than a speculative rewrite.

Per-operation cancellation is cooperative. A cancellation request takes effect at the next progress checkpoint; native libraries and individual file reads can take time to return. Completed reports, saved decisions and deliberately exported files remain available.
